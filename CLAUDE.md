This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DARFO5 HRMS — a Human Resource Information System built on the Laravel + React (Inertia) starter kit. Laravel 12 backend, React 19 + TypeScript frontend, Inertia.js for server-driven SPA routing (no separate REST/JSON API layer for pages), Tailwind CSS v4, shadcn/radix-ui components. Core domains: employee profiles, Personal Data Sheet (PDS) forms, service records, leave requests/credits, reference data (divisions, sections, positions, eligibilities, degrees), announcements, notifications, and PDF generation (Browsershot/dompdf) for official forms (PDS, Service Record, ARTA ID).

## Commands

### PHP / Laravel
- `composer dev` — run server + queue listener + Vite + Reverb + scheduler (`schedule:work`, drives `notifications:prune` and `announcements:delete-expired`) concurrently (primary local dev command)
- `composer dev:ssr` — same, but with Inertia SSR build/serve
- `php artisan serve` — Laravel dev server alone
- `composer lint` — format PHP with Pint (`pint --parallel`)
- `composer test:lint` — check Pint formatting without writing (`pint --parallel --test`)
- `composer test` — clears config cache, runs `test:lint`, then `php artisan test` (Pest)
- `php artisan test --filter=TestName` — run a single test
- `php artisan test tests/Feature/DashboardTest.php` — run a single test file
- `php artisan migrate` / `php artisan migrate:fresh --seed` — run migrations (seeders create `superadmin`/`admin` roles + default users, reference data, Philippine locations)

### JS / frontend
- `npm run dev` — Vite dev server (usually run via `composer dev` instead)
- `npm run build` / `npm run build:ssr` — production build
- `npm run lint` — ESLint with `--fix`
- `npm run format` / `npm run format:check` — Prettier over `resources/`
- `npm run types` — `tsc --noEmit`
- `npm run start` — concurrently runs `php artisan serve` + `npm run dev` + `php artisan reverb:start` (no queue listener; prefer `composer dev`)

## Architecture

### Inertia page/controller pattern
Controllers return `Inertia::render('PageName', [...props])`; the string maps to a file under `resources/js/pages/` (e.g. `Inertia::render('pds/Index', ...)` → `resources/js/pages/pds/Index.tsx`). Page component names/paths follow the folder structure under `resources/js/pages` (`Admin/`, `SuperAdmin/`, `Employee/`, `pds/`, `settings/`, `public/`, etc.), mirroring the controller namespaces under `app/Http/Controllers`.

### Wayfinder — generated routes/actions, do not hand-edit
`resources/js/routes/**` and `resources/js/actions/**` (plus `resources/js/wayfinder/`) are generated by `@laravel/vite-plugin-wayfinder` from the PHP route definitions (each file has a `@see` pointing back to the controller method and route). They regenerate automatically on `npm run dev`/`vite build` whenever `routes/*.php` or controller signatures change. Use these generated helpers from frontend code (e.g. `import { store } from '@/routes/admin/service-records'`) instead of hardcoding URLs — but never edit the generated files directly; change the underlying route/controller and let Wayfinder regenerate.

### Authorization: role-based via spatie/laravel-permission
Roles: `superadmin`, `admin` (HR staff), `employee` (implicit default — no explicit role check, i.e. any authenticated+verified+approved user). Route groups in `routes/web.php` gate by `role:superadmin`, `role:admin`, or `role:admin|superadmin` middleware. `HandleInertiaRequests` shares `auth.user.roles` and `auth.user.permissions` to the frontend for UI-level gating. New admin-only backend features should go in `app/Http/Controllers/Admin/` (or `SuperAdmin/`) and route groups with the matching `role:` middleware — don't rely on frontend-only checks.

### User approval + email verification flow
Registration → OTP-based email verification (`app/Http/Controllers/OtpController.php`; `User::sendEmailVerificationNotification()` is intentionally a no-op since Fortify's default mailer isn't used) → verified but unapproved users land on `/pending-approval` → an admin/superadmin approves via `EmployeeController::approve`/`toggleApproval`. `is_approved` is a separate boolean from `email_verified_at`; check both where access should be gated on a fully onboarded account. `NewUserRegistered`/`Verified` events notify admins (`app/Listeners`, `app/Notifications`) of pending approvals — surfaced in the shared `unreadNotificationsCount` Inertia prop.

### PDS (Personal Data Sheet) domain
The PDS is modeled as one row per section per user across many tables (`PdsPersonalInfo`, `PdsFamilyBackground`, `PdsChild`, `PdsEducation`, `PdsEligibility`, `PdsWorkExperience`, `PdsVoluntaryWork`, `PdsTraining`, `PdsOtherInfo`, `PdsQuestion`, `PdsReference`, `PdsGovernmentId`), all keyed by `user_id` (list-type sections ordered by `sort_order`). `PdsController::saveSection` dispatches by section name to per-section save methods. `app/Http/Controllers/Concerns/BuildsPdsData.php` centralizes assembling this data; `PdsPdfController`/`WesController` reuse it (and the same Blade views under `resources/views/pds/`) to render the PDF and the browser-preview route so preview and PDF output never drift. In local env, `routes/web.php` exposes `/pds/html-preview/{userId?}` and `/service-records/html-preview/{userId?}` that render the exact PDF Blade view as HTML for fast iteration on PDF layouts — reload the tab after Blade changes.

### PDF generation
Two PDF paths coexist: `spatie/browsershot` (headless Chrome via `app/Support/PdfBrowsershot.php`, used for PDS/WES/Service Record/ARTA ID — pixel-accurate HTML/CSS rendering) and `barryvdh/laravel-dompdf` (available as a dependency). Service record PDF logic lives in `app/Services/ServiceRecordPdfService.php` (`buildHtml($user, preview: bool)`), reused by both the preview route and `ServiceRecordPdfController`/`ServiceRecordBulkPdfController`.

### Real-time / broadcasting
`laravel/reverb` (self-hosted WebSocket server) + `laravel-echo`/`pusher-js` on the frontend, configured via `app/Providers/BroadcastServiceProvider.php` and `routes/channels.php`. Notifications (`app/Notifications`) rely on this for live delivery; `php artisan reverb:start` must be running locally (handled by `composer dev`).

### Leave
Two filing paths share `leave_requests` and are told apart by `form_type`:
- **`simple`**: the Wellness Leave modal on `/my-leave`. It files WL only (`LeaveService::simpleFormLeaveTypes`) and is open to every employment type. JO/COS/Pakyaw can only use this path (CSC MC 41 s.1998).
- **`csc6`**: CSC Form 6 (Application for Leave), **Permanent only**. The server enforces this in `StoreLeaveApplicationRequest::authorize()` and `LeaveApplicationController`. Employees use the two-step page `/my-leave/apply` (Fill, then Review). Review shows the real PDF of the unsaved input (`POST /my-leave/apply/preview`) with a DRAFT watermark. `leave_types.csc_form_order` sets the order of the 6.A checkboxes (NULL = not on the form).

**CSC Form 6 PDF:**
- `LeaveApplicationPdfService` renders `resources/views/leave/csc-form-6.blade.php` for the preview, the filed form, the admin review and the archive.
- On approve/deny, the final PDF is saved to `storage/app/private/leave-forms/{id}.pdf` (`final_pdf_path`), and later requests serve that archived copy.
- Items 1–5 are frozen at filing in `applicant_snapshot`. Salary comes from the latest service record, falling back to the salary grade.
- For fast layout iteration in local env, `/leave/html-preview/{id}` renders the same Blade view as HTML.
- Signatory names and the form timezone come from `config/leave.php` (`LEAVE_*` env keys).

**Admin review:** `/admin/leave/{id}/review` (`role:admin|superadmin`, like all admin leave routes) is where one admin fills section 7 (7.A–7.D) and approves or denies in one step. 7.A is pre-filled by `LeaveService::certificationFor()`. A `csc6` request can't be approved without section 7, so it is excluded from the dashboard's bulk actions. On approval only 7.C "days with pay" is deducted (`LeaveService::chargedDays`).

**Placeholder:** only VL, SL and WL track credits (`leave_types.tracks_credits = true`). Forced Leave (FL) has no balance of its own: `charge_to_leave_type_id` points it at VL, per CSC rules, so it reserves and deducts VL credits. `LeaveService::creditFor()` handles all of this. Every other CSC Form 6 type (ML, PAT, SPL, SOLO, STUDY, VAWC, RL, SLW, CL, AL, OTH) has `tracks_credits = false`: it can be filed, but no balance is created, checked or deducted. The accrual, cap and reset rules for these types are **pending HR policy input**, so this is not a finished credit model. The retired `PL` ("Privilege Leave") row stays inactive only so that historical references still resolve.

### Reference/lookup data
`Division`/`Section` (hierarchical, with a `move` endpoint for reordering), `Position`, `Eligibility`, `GraduateProgram`, `BachelorsDegree` are admin-managed CRUD reference tables under `admin/reference-data/*`, each with a dedicated controller in `app/Http/Controllers/Admin/ReferenceData/` and page in `resources/js/pages/Admin/ReferenceData/`. Philippine location data (`PhProvince`/`PhCity`/`PhBarangay`) is seeded once and served read-only via `LocationController`.

### Public employee ID / QR endpoint
`/employee/{employeeNumber}` (`PublicEmployeeController`) and the ARTA ID preview/download routes are unauthenticated-by-design public-facing pages (throttled), used for QR-code employee verification — keep exposed fields minimal when touching these.
